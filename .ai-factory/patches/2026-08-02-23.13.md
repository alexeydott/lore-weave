# Preserve actual entity-kind state across preview and duplicate conflicts

**Date:** 2026-08-02 23:13
**Files:** `services/glossary-service/internal/api/kind_votes.go`, `services/glossary-service/internal/api/kind_votes_handler.go`, `services/glossary-service/internal/api/extraction_handler.go`, `services/glossary-service/internal/api/kind_votes_integration_test.go`, `scripts/backfill-entity-kind-votes.py`
**Severity:** critical

## Problem

A duplicate target could block a live entity re-kind while extraction still reported the
candidate kind and emitted an outbox event for it, leaving knowledge-service out of sync with
glossary-service. Separately, the default backfill preview persisted vote-ledger rows even
though it described itself as a dry run.

## Root Cause

`applyKindResolution` returned whether a primary kind actually moved, but
`resolveEntityKind` discarded that result. The extraction caller used the requested
resolution instead of the persisted state. The import handler used a transaction for preview
calculation but committed it unconditionally, conflating a simulation with an apply operation.

## Solution

Propagate the actual move result through `resolveEntityKind`; only report and emit a changed
kind when the database applied it. Keep the existing full resolution calculation for previews,
but roll its transaction back when `apply=false`. Add DB-backed HTTP regressions for both paths
and update backfill documentation. Structured `[FIX]` logs make blocked re-kinds and rolled-back
previews observable without logging entity names or secrets.

## Prevention

- Treat a computed candidate and a persisted state transition as separate values.
- Gate downstream events on the actual database mutation result, especially after uniqueness or
  conflict guards.
- A dry run must leave every durable table unchanged; execute it against a transaction that is
  explicitly rolled back.
- Cover transaction/outbox behavior with real DB integration tests, not only pure resolver tests.
